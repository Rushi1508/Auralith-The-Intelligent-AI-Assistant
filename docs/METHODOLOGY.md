# Evaluation methodology

Everything in `results/` was produced by `eval/run_eval.py` and `eval/sweep.py`
on the corpus pinned in `eval/corpus/fetch_corpus.py`. This document explains
how the numbers are made and, more importantly, what they do not mean.

## Corpus

Three open-access arXiv papers, 50 pages total, fetched by SHA-256 pin:

| doc_id | paper | pages | sha256 (first 12) |
|---|---|---|---|
| `attention` | Attention Is All You Need (1706.03762) | 15 | `bdfaa68d8984` |
| `bert` | BERT: Pre-training of Deep Bidirectional Transformers (1810.04805) | 16 | `5692a5514787` |
| `rag` | Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (2005.11401) | 19 | `23e3249e9a1e` |

The papers are topically adjacent on purpose. All three are NLP papers that cite
each other, so retrieval has to discriminate between similar documents rather
than just pick the right topic. Three unrelated documents would make the task
artificially easy.

The checksums are load-bearing: page numbers are the ground-truth labels, and a
silently updated arXiv version would shift them and invalidate every recall
number without any test failing.

## Question set

28 questions in `eval/questions.json`, written by reading the extracted page
text of the pinned PDFs. Nothing was generated by a model, because a
model-written eval set inherits the model's misconceptions and then scores the
pipeline against them.

| type | n | what it probes |
|---|---|---|
| factoid | 16 | a single specific number or name |
| conceptual | 5 | a mechanism, needs paraphrase matching |
| lexical | 4 | hinges on a rare exact token (`FAISS`, `P100`, `WordPiece`) |
| cross-document | 1 | requires joining two papers |
| unanswerable | 2 | the answer is nowhere in the corpus |

The unanswerable questions are the ones that make the set honest. Both are
phrased to look exactly like answerable neighbours — "What BLEU score did the
Transformer achieve on WMT 2014 English-to-**Romanian**?" mirrors a real
English-to-German question. Without them, a pipeline that confidently fabricates
an answer to everything scores identically to one that knows when to stop.

## Retrieval metrics

Relevance is **page-level**: a retrieved chunk counts as relevant iff its
`(doc_id, page)` pair is one a human verified as answering the question.

`PyPDFLoader` emits one Document per page and `split_documents` only splits
*within* a Document, so a chunk can never straddle a page boundary. That gives
every chunk exactly one page label for free.

Why page-level and not span-level:

* It is objective and model-free, so retrieval numbers are not contaminated by
  the thing being evaluated.
* It stays valid across every chunking scheme, so sweep rows are comparable.
  A span-level label would have to be re-derived per chunk size.

The cost is that it is coarse: a chunk from the right page that misses the exact
sentence still scores as a hit. This bias flatters *large* chunks more than
small ones (a 927-token page-chunk covers the whole page trivially), so the
Phase B gains from smaller chunks are if anything understated.

| metric | what it adds |
|---|---|
| `recall@k` | fraction of the question's relevant pages recovered |
| `hit@k` | did any relevant page appear at all |
| `MRR` | 1/rank of the first relevant chunk — **the only rank-sensitive metric** |
| `precision@k` | how much of the context window is not noise |

MRR earns its place because reranking reorders *within* the top k. `recall@k`
is rank-insensitive by construction and literally cannot see a cross-encoder
moving the right passage from rank 4 to rank 1.

**`recall@k` is not comparable across different k.** It rises with k
mechanically. When reading the k sweep, `hit@k` and `MRR` are the columns that
plateau and therefore the ones that carry information.

Retrieval metrics are averaged over the 26 **answerable** questions only.
Unanswerable questions have no relevant page by construction, so including them
would subtract a constant that says nothing about retrieval quality. They are
scored separately as `abstention_accuracy`.

## Answer correctness

An LLM-as-judge (`qwen2.5:7b`) compares the generated answer against the
human-written reference. Design constraints:

* **Binary verdict, not a 1–5 scale.** A 7B model cannot reliably tell a 3 from
  a 4, and averaging unreliable ordinals produces a number that looks precise
  and is not.
* **The judge never sees the retrieved passages**, only the question, the gold
  answer and the candidate. Otherwise it would partly be grading whether the
  answer follows from what was retrieved, which is a different question.
* **The judge is a different, larger model than the generator** (`qwen2.5:7b`
  grading `llama3.2:3b`). A model grading its own output is measurably
  self-favouring.
* **Abstention is a deterministic string check**, never a model call. It is the
  one part of scoring with no ambiguity.

### Judge reliability is measured, not assumed

`python eval/run_eval.py --validate-judge` scores the judge against 10
hand-labelled cases including adversarial ones — right number/wrong unit,
paraphrase with no shared vocabulary, correct fact contaminated with a
fabricated detail.

**Result: 9/10 = 90% agreement** (`results/judge_validation.json`).

The single disagreement is diagnostic and is not swept under the rug: the judge
accepted *"They used the Adam optimizer"* against a reference requiring the beta
values, i.e. it is **lenient toward incomplete answers**. So
`answer_correctness` is biased slightly **upward**. It correctly caught both
hallucination cases and the wrong-unit case, which are the failure modes that
matter most here.

A deterministic `keyword_score` runs alongside the judge on every question. It
is too strict to be a headline metric, but divergence between the two is how
judge drift gets caught rather than trusted.

## Run settings

| setting | value | why |
|---|---|---|
| generator | `llama3.2:3b` (Ollama, CPU) | local, reproducible, free |
| judge | `qwen2.5:7b` (Ollama, CPU) | larger and different from the generator |
| embeddings | `all-MiniLM-L6-v2`, normalised | MiniLM is trained for cosine; Chroma's default space is L2, and normalising makes L2 a monotone function of cosine so the ranking is the one the model intends |
| cross-encoder | `ms-marco-MiniLM-L-6-v2` | local reranking |
| temperature | 0.0 | reproducibility |
| `max_output_tokens` | 512 | the longest reference answer is two sentences, so this is several times the headroom any correct answer needs; its job is to stop a small model rambling and stalling a run |

Generation settings are applied **uniformly to every configuration**, so they
cannot bias a comparison between configs. They do bound the absolute
`answer_correctness` number, which is why retrieval metrics — which involve no
model at all — are the ones the configuration decisions were made on.

### Generator and judge are batched, not interleaved

The harness generates all answers, evicts the generator, then judges all
answers. This is a measured fix, not a preference: interleaving kept both
models resident (7.6 GB of weights on a 15.6 GB machine, ~1.1 GB free) and
drove the box into paging — a 28-question run had not completed after 57
minutes. Evicting between phases returned ~8 GB. See
`auralith.providers.unload_model`.

## Why sweeps are retrieval-only

`recall@k`, `hit@k`, `MRR` and `precision@k` are computed from chunk metadata
alone — no generator, no judge, no LLM call. A retrieval-only pass over 28
questions takes **~2 seconds**. A full end-to-end pass with generation and
judging on local CPU models takes **~45–60 minutes**.

So sweeps are exhaustive and cheap, and only the finalists pay for an
end-to-end run. Coupling the two would have made Phase B/C take days and would
have added generator noise to a measurement that does not need it.

## Known limitations

These are real and an interviewer should be able to find them stated here
rather than have to extract them.

1. **28 questions is a small sample.** One question is worth ~3.8 percentage
   points of recall. Differences below roughly 0.04 are not distinguishable from
   noise, and no confidence intervals are computed. The Phase B chunking result
   (+0.19) is far outside that band; the Phase C hybrid result (+0.0045) is well
   inside it, which is exactly why it was rejected.

2. **The sweep is sequential and greedy, not a grid.** Chunking was optimised
   first, then k on the chunking winner, then Phase C features on that. Chunk
   size and k interact — smaller chunks carry less of the answer each, so the
   best k shifts with chunk size — so this can land in a local optimum. A full
   grid was not run.

3. **Page-level relevance is coarse** (see above).

4. **The generator is a 3B model on CPU.** Answer correctness is bounded by it
   and is not a statement about what the retrieval pipeline could achieve with a
   frontier model. Retrieval metrics are model-independent and do transfer.

5. **Single seed, no repeats.** Temperature is 0 everywhere, but Ollama
   generation is not guaranteed bit-identical across runs, and no
   variance-across-seeds was measured.

6. **The eval set was written by the same author as the pipeline.** Questions
   were written from the papers before any results were seen, but this is not a
   held-out set produced by an independent party.
