## Where the failures moved

| | baseline | tuned |
|---|---|---|
| retrieval missed the page entirely | 9/26 | 2/26 |
| retrieval found it, answer still wrong | 9/26 | 13/26 |

This is the most useful thing in the run. **Retrieval failures fell 9 -> 2
(-78%), while generation-side failures rose 9 -> 13.** The tuned
pipeline now puts the correct page in front of the model for 24 of 26
answerable questions; the binding constraint is no longer retrieval but the 3B
generator's ability to state every required fact from a passage it was given.

## Reading these numbers honestly

- **answer_correctness improved 30% relative** (10 -> 13 of 28). The direction
  matches the retrieval gain, which is the result the tuning predicted.
- **abstention_accuracy 0.50 -> 1.00 rests on n=2.** That is one question
  flipping. It is reported because it was measured, but it is not evidence of
  anything on its own.
- **false_abstention_rate got worse: 0.1154 -> 0.1923** (3 -> 5 of 26).
  The tuned config refuses more questions it has evidence for. Three of the
  five wrongly-refused questions had the correct passage retrieved, so this is
  a generator failure, plausibly aggravated by k=6 giving it more passages to
  sift than k=4 did. This is a real regression and is not averaged away here.
- **Latency rose 11s/question (13%)**, the cost of k=6 over k=4.
- **Absolute correctness is low in both columns** (10/28 and 13/28). That is a
  statement about a 3B model on CPU, not about the retrieval pipeline. The
  judge is also known to be lenient toward incomplete answers
  (`results/judge_validation.json`), which biases both columns upward equally.
- **28 questions.** One question is worth ~3.6 points of overall correctness.
  Only the retrieval-failure drop (9 -> 2) and the correctness delta are
  large enough to be worth much; the rest is within noise.

Run integrity: **0 judge parse failures and 0 generation errors** across both
runs (56 generations, 56 judge calls).
